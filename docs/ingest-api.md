# API загрузки данных (ingest)

Внешняя система передаёт порталу факты — маршрут и события. Портал сам решает, принять ли событие, к
какому этапу оно относится, какую фазу ставит, что пишет в журнал и что видит клиент.

## Решения

- Передача — снимок перевозки за один вызов, повтор безопасен.
- Логика — C# в SpeditionManagerApi (`PortalIngestService`, `EventEngine`).
- Вход — ключ сервиса в заголовке `X-Api-Key`, доступ только к `/api/portal/ingest`.
- Разбор SM — в выгрузке: портал знает только свои коды и правила.
- Типы событий однозначные: «Загружен» или «Выгружен», без вариантов.
- Учётки сотрудников — без паролей: пароль человек задаёт сам через «Забыли пароль».
- Событие пропало из внешней системы без отмены — не удаляется, а отменяется с причиной «Нет во внешней
  системе».

## Кто за что отвечает

| Выгрузка (переводчик SM) | Портал |
|---|---|
| какие перевозки выгружать (окно, изменённые, повтор упавших) | перевозка, клиент, участники |
| маршрут: этапы по порядку, перевозчик, транспорт, склад, плановые даты | этапы, `removed_utc` у пропавших этапов с событиями |
| пункт SM → однозначный код события портала, события из двух частей | движок: этап, фаза, конфликт |
| журнал РК: исправления, «Удалено», события дня | журнал фаз, ATA / ATD |
| время SM → UTC | повторы, показ клиенту, автопубликация |

## Вызовы

Все пути — `/api/portal/ingest/…`. В пути — номер во внешней системе, ответы с id — id портала.
Ошибки: 400 — форма или неизвестный код (тип события, этапа, роль, право), 404 — перевозки нет, 409 —
e-mail у пользователя с другим номером.

| Вызов | Тело | Ответ |
|---|---|---|
| `PUT users/{external_id}` | `email`, `permissions[]` | `id` пользователя; права добавляются |
| `PUT clients/{external_id}` | `name` | `id` клиента (выдаёт портал) |
| `PUT shipments/{external_id}` | `tracking_number`, `tracking_subnumber`, `client_id`, `members[{role, user_id}]` | `id` перевозки; лишние участники удаляются |
| `PUT shipments/{external_id}/route` | `stages[]` — все этапы по порядку | что изменилось, `conflicts` |
| `POST shipments/{external_id}/events` | `events[]` — новые и изменённые, `cancel[{external_id, reason, at_utc}]` | то же |
| `GET shipments/{external_id}/events` | — | `external_ids` действующих событий |

**Этап:** `external_id`, `type` (код типа этапа), `place_name`, `country`, `custodian {external_id, name}`,
`object_type`, `object_units`, `storage`, `eta_utc`.

**Событие:** `external_id`, `type` (код портала), `source` (`driver`, `rk`), `occurred_utc`, `received_utc`,
`date_only`, `comment`, `fault` (вина остановки: `customer`, `carrier`, `external`; пусто — по умолчанию типа),
`address`, `geo {lat, lon}`, `author_external_id`,
`cancelled {at_utc, by_external_id, reason}`. Событие-отмену портал создаёт сам.

Пропавшее событие портал не угадывает: выгрузка берёт `GET …/events`, сравнивает со своими и шлёт `cancel`.

## Как движок обрабатывает вызов

Движок прогоняет все события перевозки при каждом вызове маршрута или событий и сверяет с результатом
журнал фаз, состояние этапов, ATA / ATD, повторы и показ клиенту. Итог тот же, что «прогнать заново с
места изменения», а код проще. Правила — в [overview.md](overview.md).
