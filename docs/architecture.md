# Архитектура и развёртывание

## Общая схема

```
          ┌──────────────────────── сервер клиента ────────────────────────┐
          │                                                                │
 PWA  ───►│  reverse proxy (TLS)  ──►  plobi-app (API + WebSocket + PWA)   │
(водитель,│                                  │            │                │
 диспетчер)                                  ▼            ▼                │
          │                            PostgreSQL    файловое хранилище    │
 TMS/1С/  │                                          (том или S3/MinIO)    │
 ERP  ───►│  REST API (токены интеграций)                                  │
          │  ◄── вебхуки об изменениях ───                                 │
          └────────────────────────────────────────────────────────────────┘
```

## Контейнеры

Каждый компонент работает в **своём контейнере**:

| Контейнер | Что внутри | Данные |
|---|---|---|
| `plobi-app` | приложение: API, WebSocket, статика PWA | не хранит ничего, можно пересоздавать и обновлять в любой момент |
| `plobi-db` | PostgreSQL | том `db-data` |
| `plobi-files` (необязательно) | MinIO, S3-совместимое хранилище файлов | том `files-data`; без него файлы лежат в томе приложения |

- Поставка — `docker-compose.yml` с этими сервисами.
- Приложение подключается к базе по `DATABASE_URL`, поэтому вместо
  контейнера `plobi-db` можно указать **внешнюю PostgreSQL** компании (свой
  кластер, облачная БД), а `plobi-app` оставить как есть.
- Обновление приложения выглядит так: новый образ `plobi-app`, база не
  трогается. Миграции применяет приложение при старте.
- Контейнер `plobi-app` не хранит состояние, поэтому при росте нагрузки
  можно запустить несколько его копий за балансировщиком.

«Модульный монолит» из [engineering.md](engineering.md) — про устройство
кода внутри `plobi-app`: одно приложение, разделённое на независимые
модули. К тому, сколько контейнеров запускается, это отношения не имеет.

## Стек

| Слой | Выбор | Почему |
|---|---|---|
| Бэкенд | TypeScript, Node.js, Fastify | один язык с фронтендом, быстрый, хорошая генерация OpenAPI |
| БД | PostgreSQL 16 | надёжная, JSONB для пользовательских полей, у клиентов обычно уже есть опыт |
| ORM и миграции | Drizzle ORM | типобезопасность, SQL-миграции применяются автоматически при старте контейнера |
| Realtime | WebSocket | чат, новые события, статусы «прочитано» |
| Фронтенд | React, Vite, vite-plugin-pwa | PWA «из коробки», service worker |
| Офлайн на клиенте | IndexedDB (Dexie) | очередь неотправленных событий и сообщений, кэш рейса |
| Push | Web Push (VAPID) | работает без Google и Apple-аккаунтов разработчика; ключи генерируются на сервере клиента |
| Файлы | S3-совместимое API или локальный диск | фото, документы, голосовые |

## Self-hosted и лицензирование

- Разработчик не получает никаких данных: нет телеметрии, нет «звонков домой».
- Лицензия — подписанный файл (JWT, Ed25519) с названием компании, сроком и
  лимитом активных пользователей. Приложение проверяет подпись встроенным
  публичным ключом, поэтому интернет для проверки не нужен.
- Обновления: новый тег образа. Миграции БД применяются при старте.
- Резервное копирование (`pg_dump` и том с файлами) лежит на клиенте; в
  документации поставки будет готовый скрипт.

## Офлайн-режим водителя

Связь на трассе пропадает, поэтому:

1. Каждое событие и сообщение получает UUID **на клиенте** и хранит время
   `occurred_at` и координаты на момент действия.
2. Запись сначала попадает в IndexedDB, затем фоново отправляется на сервер.
3. Сервер принимает запись идемпотентно (повтор с тем же UUID не создаёт
   дубль) и дополнительно сохраняет `received_at`.
4. Диспетчер видит оба времени: когда событие произошло и когда оно дошло.

## Зеркала (резервные адреса)

Зачем: основной домен может быть заблокирован в стране, где сейчас водитель,
может упасть провайдер или DNS. Бэкенд и база при этом одни, а **адресов
несколько**: разные домены, IP-адреса, прокси или CDN у разных провайдеров.
Отказоустойчивость самого сервера (кластер, реплики БД) — отдельная тема, а
зеркала решают задачу «сервер жив, но до него не достучаться».

### Кто за что отвечает

| Компания-покупатель | Приложение Plobi |
|---|---|
| поднимает зеркала: домены, IP, прокси, сертификаты | хранит список зеркал в настройках |
| решает, сколько их нужно и где | передаёт список водителям и переключается между адресами |
| сообщает водителям новые адреса параллельным путём, если все известные заблокированы | даёт для этого QR-код или ссылку-приглашение и ручной ввод адреса |

Разработчик продукта зеркала не предоставляет и не обслуживает.

### Как адреса попадают к водителю

1. **Через приложение.** Админ вносит адреса в настройки, и каждый клиент
   получает обновлённый список при следующей связи с сервером через любой
   доступный адрес. Поэтому новые зеркала лучше добавлять **заранее**, пока
   старые ещё работают.
2. **Параллельным путём**, когда все известные водителю адреса уже
   недоступны. Админ генерирует QR-код или ссылку-приглашение и отправляет
   его любым каналом: SMS, email, звонок, бумага в кабине. Водитель сканирует
   код или вводит адрес вручную на экране входа. Это работает и для уже
   установленного приложения, данные и офлайн-очередь сохраняются.

### Настройка

Администратор задаёт список адресов в разделе «Сеть → Зеркала» (или
переменной `PUBLIC_URLS` при развёртывании):

```
1. https://chat.company.com        основной
2. https://chat.company-backup.net резервный домен у другого регистратора
3. https://203.0.113.10            прямой IP (сертификат на IP)
4. https://proxy.other-provider.io обратный прокси в другом облаке
```

При первой установке экземпляр генерирует `instance_id` и ключ подписи
Ed25519.

### Как работает клиент

1. **Список зеркал** приходит с сервера (`GET /api/v1/client-config`) вместе с
   подписью и хранится в IndexedDB. Подпись проверяется публичным ключом
   экземпляра, который клиент запоминает при первом подключении. Поэтому
   подменить список через перехваченный адрес нельзя.
2. **Оболочка PWA закэширована** service worker'ом, так что приложение
   открывается, даже если основной домен недоступен.
3. **Переключение.** Запрос идёт на текущий адрес. При сетевой ошибке,
   таймауте или ответе 502/503/504 клиент пробует следующий адрес по
   приоритету. Удачный адрес становится текущим. Раз в несколько минут клиент
   фоном проверяет более приоритетные адреса через `/api/v1/health` и
   возвращается на них.
4. **Проверка подлинности.** `/health` возвращает `instance_id`. Если он не
   совпадает с ожидаемым, адрес отбрасывается: это не наш сервер.
5. **WebSocket** переподключается по тому же списку.
6. **Сессия работает на любом зеркале:** токен передаётся в заголовке
   `Authorization` (не в cookie), CORS разрешён для всех адресов из списка,
   ссылки на файлы относительные.
7. **Первое подключение, когда основной адрес уже заблокирован:** админ выдаёт
   водителю QR-код или ссылку-приглашение. В них зашиты `instance_id`,
   публичный ключ и список адресов. Ещё можно вручную ввести адрес на экране
   входа.
8. **Индикатор** в интерфейсе показывает, через какое зеркало сейчас идёт связь.

### Ограничения

- Установленная PWA привязана к адресу, с которого её установили. Если этот
  адрес недоступен, приложение работает из кэша через зеркала, но
  **обновление самого приложения** придёт, только когда адрес снова станет
  доступен. Поэтому сервер поддерживает клиентов предыдущей версии API.
- Если открыть другое зеркало в браузере напрямую, получится отдельное
  приложение с отдельным хранилищем: офлайн-очередь у него своя.
- Web Push доставляется через сервисы браузеров (Google, Apple, Mozilla) и от
  наших адресов не зависит. Если эти сервисы недоступны, уведомления не
  придут, но сообщения подтянутся при открытии приложения.

## Ограничения PWA, о которых нужно знать

- **Фоновое отслеживание GPS в PWA невозможно.** Геопозиция снимается только в
  момент действия водителя (событие, сообщение) или пока приложение открыто.
  Для непрерывного трекинга нужны данные с бортового GPS-трекера, их можно
  передавать через API. Если позже понадобится трекинг с телефона, можно
  обернуть PWA в нативную оболочку (Capacitor) без переписывания.
- **iOS:** push-уведомления работают только у PWA, установленного на домашний
  экран (iOS 16.4+).
- Фоновая синхронизация (Background Sync) есть в Android и Chrome. На iOS
  очередь отправляется при следующем открытии приложения.

## Безопасность

- Пароли хранятся как хэши Argon2id. Сессии — короткий access-токен и
  refresh-токен.
- Можно подключить вход через корпоративный SSO (OIDC), это есть в плане работ.
- У каждой интеграции свой API-токен с набором разрешений (scopes).
- Журнал аудита: кто, что и когда изменил.
