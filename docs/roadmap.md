# План работ

Два главных отличия продукта, и оба должны быть в пилоте:

1. **Рейс:** этапы, фазы, события, требования, фото процесса, простои.
2. **Корпоративный мессенджер, который не блокируют:** свой сервер у
   компании, зеркала, чаты в контексте перевозки и между любыми сотрудниками.

## Шаг 1. Ядро и каркас
- Монорепозиторий и модульная структура (см. [engineering.md](engineering.md)).
- Пакет `core`: автоматы состояний и фаз (профили точки и транзита), функция
  «события → фаза и состояние», проверка ярлыков и требований. Чистый код без
  ввода-вывода, работает на сервере и в PWA, полностью покрыт тестами.
- Сервер: пользователи, вход, роли; первый админ создаётся при первом
  запуске. OpenAPI и Swagger UI.
- `docker-compose.yml`: отдельные контейнеры `plobi-app` и `plobi-db`, миграции
  применяются автоматически при старте приложения, внешняя БД по `DATABASE_URL`.
- Справочники с базовым набором, их редактирование в админке.
- **Раздел «Автоматы» в админке**: схемы состояний и фаз, карта каждого типа
  этапа с событиями, ролями и требованиями на переходах; проверка настроек;
  симулятор рейса.

## Шаг 2. Рейс у водителя и диспетчера
- **Справочник мест**: адрес, координаты, контакты, часы работы.
- Создание рейса с этапами, тегами и требованиями: через API и в интерфейсе.
- **Требования на этапах** — один список того, что водитель видит и делает:
  прочитать (с контактом «Позвонить», фото, точкой на карте, файлом),
  подтвердить «Ознакомлен», снять фото, приложить документ и т.д.; показ по
  фазе.
- Экран водителя: список рейсов, карточка рейса, кнопки событий по ярлыкам,
  формы по схеме полей, фото с камеры, **чек-лист перехода**.
- Экран диспетчера: список рейсов, таймлайн, свои события, снятие
  требований, инциденты, конфликты.
- Офлайн-очередь событий и пересчёт по `occurred_at`.

## Шаг 3. Мессенджер и связь
- Чат рейса с карточками событий в ленте, личные и групповые чаты между
  любыми сотрудниками.
- Файлы, фото, голосовые, статус «прочитано», WebSocket.
- Офлайн-очередь сообщений, как у событий.
- **Поддержка зеркал** (сами зеркала поднимает компания): список адресов в
  настройках, переключение, подписанный конфиг, QR-код или ссылка для
  передачи адресов водителю параллельным путём, ручной ввод адреса.
- Уведомления: Web Push плюс резерв внутри приложения (см. ниже).

**→ Пилот на реальных рейсах после шага 3.**

## Шаг 4. Интеграции и поставка
- Токены интеграций со scopes, upsert по `external_id`, `act_as`.
- Вебхуки с подписью и повторами.
- Приём позиций с GPS-трекеров, карта рейса.
- Лицензионный ключ, лимит пользователей.
- Документация для администратора клиента: установка, обновление, бэкап.

## Потом

- **Модуль путевых листов** (планируется, пока не прорабатывается).
- **Роли медика и механика** (права пока не определены).
- SSO (OIDC / Keycloak / AD), мультиязычность интерфейса (ru, en, …).
- Справочник ТС и прицепов, шаблоны рейсов.
- Отчёты: простои, опоздания, выполнение окон, нарушения требований.
- Нативная оболочка (Capacitor) для фонового GPS и push без сервисов
  Google и Apple, если понадобится.

## Риск: push-уведомления при блокировках

Web Push доставляется **через сервисы Google, Apple и Mozilla**. Там, где
блокируют мессенджеры, иногда ограничены и эти сервисы, и наши зеркала тут
не помогут. Поэтому:

- пока приложение открыто, сообщения приходят по WebSocket через зеркала,
  без push;
- при открытии приложения всё непрочитанное подтягивается сразу;
- критичные события можно дублировать **по SMS** через шлюз, который
  подключит сама компания;
- если этого окажется мало, нативная оболочка позволит подключить свой
  канал уведомлений.

Это надо проверить на пилоте в реальных странах рейсов.
