# Принципы разработки

Цель: код, который легко **читать**, **поддерживать** и **расширять**.
Продукт будет жить годами и устанавливаться у разных компаний с разными
настройками.

## 1. Модульный монолит

Одно приложение (контейнер `plobi-app`; база — в своём контейнере
`plobi-db`), но внутри — **независимые модули с явными границами**. Это проще в поставке и сопровождении, чем микросервисы, а
порядок в коде такой же.

```
packages/
  core/              чистая доменная логика: автоматы, ярлыки, требования
                     (без БД, сети, фреймворков; общий для сервера и PWA)
  api-contract/      типы и схемы API (OpenAPI), общие для сервера, PWA и интеграторов
apps/
  server/
    src/
      modules/
        identity/        пользователи, роли, вход, токены
        catalog/         типы этапов, события, требования, правила (тип, теги, клиент, место)
        directory/       места и клиенты, требования клиента
        trips/           рейсы, этапы, журнал событий, инциденты; пересчёт через core
        automata/        раздел «Автоматы»: схемы, карта типа этапа, симулятор
        messaging/       чаты, сообщения, «прочитано»
        files/           вложения, хранилище (диск / S3)
        notifications/   web push, SMS-шлюз, внутренние уведомления
        integrations/    токены интеграций, вебхуки, приём GPS
        settings/        зеркала, лицензия, настройки экземпляра
      platform/          общая инфраструктура: БД, логирование, конфиг, шина событий
  web/                   PWA
    src/
      modules/           те же границы: trips/, messaging/, admin/automata/ ...
      platform/          API-клиент с зеркалами, офлайн-очередь, хранилище
```

## 2. Правила границ

- **Модуль = папка с публичным входом** (`index.ts`). Снаружи можно
  импортировать только его. Внутренние файлы других модулей импортировать
  нельзя, это проверяется линтером (`eslint-plugin-boundaries`).
- **Модуль владеет своими таблицами.** Чужие таблицы напрямую не читаются:
  только через публичный интерфейс модуля.
- **Связь между модулями — через внутреннюю шину доменных событий.**
  Например, `trips` публикует `stage.phase_changed`, а `messaging` по этому
  событию кладёт карточку в чат рейса. `trips` при этом о чатах не знает.
  Новые функции подключаются подписчиками, без правки существующих модулей.
- **`core` ни от чего не зависит.** В нём нет ввода-вывода и времени
  «сейчас»: время передаётся параметром. Поэтому `core` детерминирован и
  тестируется без моков.

Инструменты: pnpm workspaces, TypeScript, Fastify + TypeBox (схемы → OpenAPI),
Drizzle ORM + PostgreSQL, Vitest.

## 3. Слои внутри модуля

```
modules/trips/
  index.ts            публичный интерфейс модуля
  domain/             правила модуля (использует core)
  application/        сценарии: createTrip, submitEvent, skipStage ...
  infrastructure/     репозитории (Drizzle), адаптеры
  http/               маршруты Fastify: только разбор запроса и вызов сценария
  *.test.ts
```

Небольшой модуль может держать слои в файлах, а не в папках:
`schema.ts` (таблицы), `service.ts` (сценарии), `routes.ts` (HTTP). Когда
модуль растёт, файлы становятся папками.

- **HTTP-слой тонкий:** проверка входа по схеме, вызов сценария, ответ.
  Бизнес-логики в нём нет.
- **Сценарий — один файл, одна операция.** Сразу видно, что умеет модуль.
- **Внешние зависимости — за интерфейсами (порты).** Хранилище файлов,
  отправка push или SMS, часы. Для тестов их легко подменить, для другого
  клиента — заменить (S3 вместо диска, другой SMS-шлюз).

## 4. Расширяемость без правки ядра

- Новые **типы этапов, события, требования, теги** — это данные в
  справочниках, а не код.
- Новый **вид поля события** или **вид требования** — новый класс по
  общему интерфейсу, зарегистрированный в реестре. Существующий код не
  меняется.
- Новый **канал уведомлений** — новый адаптер порта `Notifier`.
- **Вебхуки и шина событий** используют одни и те же доменные события, так
  что всё, что видно внутри, доступно и интеграциям.

## 5. Читаемость

- TypeScript в строгом режиме, никаких `any`.
- Имена из предметной области — те же, что в документации: `phase`, `state`,
  `stage`, `requirement`, `departed`. Один термин — одно значение (см.
  [state-machine.md](state-machine.md)).
- Небольшие файлы и функции. Комментарии объясняют **почему**, а не что.
- Ошибки предметной области типизированы (`OrderViolation`,
  `RequirementsUnmet`…), и API возвращает их с понятным кодом.

## 6. Качество

- **Тесты:**
  - `core` — исчерпывающие сценарные тесты: обычный рейс, паром, таможня с
    задержанием, офлайн-события не по порядку, конфликты, требования;
  - модули — тесты сценариев на реальной PostgreSQL в контейнере;
  - PWA — e2e основных путей водителя и диспетчера (Playwright).
- **Проверки в CI:** типы, линтер (в том числе границы модулей), тесты,
  сборка образа.
- **Миграции БД** только вперёд, каждая — отдельный файл с понятным именем.
- **Решения записываются** короткими ADR в `docs/adr/`: что решили, почему,
  какие были альтернативы.
- **Обратная совместимость API:** версия в пути (`/api/v1`), изменения
  только добавляющие; ломающие — только в новой версии.
