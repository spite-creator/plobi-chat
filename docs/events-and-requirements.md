# События и требования

Для каждого события задаётся:

1. **Где** его можно выставить. Это область применения, в интерфейсе она
   показывается ярлыками.
2. **Что** оно требует от водителя в момент выставления. Это поля события.

Отдельно от событий задаются **требования к переходу в фазу**: что должно
быть собрано на этапе, прежде чем он перейдёт в фазу (например, в «Убыл»).

Всё это проверяется общим модулем и на сервере, и на телефоне, в том числе
без связи.

## 1. Область применения события (ярлыки)

Событие доступно водителю, только если подходят **все** его ярлыки. Пустой
ярлык означает «без ограничений».

| Ярлык | Что ограничивает | Пример |
|---|---|---|
| **Вид этапа** | точка / транзит | `Остановка` — только транзит |
| **Тип этапа** | конкретные типы | `Начало погрузки` — только `loading` |
| **Вид транзита** | road / ferry / rail | `Отплытие` — только ferry, rail |
| **Фаза** | в каких фазах доступно | `Документы получены` — в фазе «Завершено» |
| **Роль** | водитель / диспетчер / наблюдатель / интеграция | `Простой подтверждён` — только диспетчер |
| **Исполнитель** | только исполнитель этапа или любой водитель рейса | при смене водителя событие ставит только новый |
| **Теги рейса / этапа** | нужен тег или, наоборот, тег запрещён | `Температура рефа` — только с тегом `#reefer` |

**Теги** — свободные метки, которые ставятся на рейс или этап вручную либо
через API: `#reefer`, `#adr`, `#customs`, `#food`, `#high_value`,
`#unaccompanied`. С их помощью одно и то же событие или требование
включается только там, где оно нужно, без отдельного типа этапа на каждый
случай.

В админке ярлыки показываются прямо на карточке события:

```
┌ Документы получены ───────────────────────────────────────────┐
│ [Точка] [Погрузка] [Выгрузка] [Фаза: Завершено] [Водитель]   │
│ Требует: фото документа ×1–5 (камера) · номер CMR             │
└───────────────────────────────────────────────────────────────┘
```

## 2. Что событие требует от водителя (поля события)

Это форма, которая открывается при нажатии кнопки события.

| Вид поля | Настройки |
|---|---|
| `photo` | мин / макс, **только камера** или камера и галерея |
| `video` | макс длительность |
| `document` | многостраничный скан (камера с обрезкой) |
| `signature` | подпись на экране (грузополучатель, кладовщик) и ФИО подписавшего |
| `scan` | штрихкод / QR: пломба, паллетные этикетки, номер прицепа |
| `number` | единица, мин / макс (температура, вес, паллеты, пробег) |
| `text` | многострочный, мин длина |
| `select` / `multiselect` | список вариантов (причина задержки) |
| `datetime` | новое ETA, время слота |
| `checklist` | набор галочек («груз закреплён», «ремни на месте») |

У каждого поля можно задать:

- `required` — обязательно ли поле;
- `show_if` — условие показа, например «Комментарий обязателен, если
  причина — Прочее».

Автоматически, без участия водителя, сохраняются:

- время события;
- GPS и точность;
- у каждого фото — время съёмки, координаты и **источник** (камера
  приложения или галерея).

Фото из галереи можно запретить или разрешить с пометкой: это защита от
«вчерашних» снимков.

## 3. Требования к переходу в фазу

Требование — это то, что **должно быть собрано на этапе до перехода в
указанную фазу**. Главный пример: перед «Убыл» с погрузки нужны фото всего
процесса, пломба и подписанная CMR.

### Чем требование отличается от поля события

| | Поле события | Требование к фазе |
|---|---|---|
| Когда заполняется | в момент события, в его форме | **в любой момент на этапе**, накопительно |
| Пример | причина задержки | фото процесса погрузки, сделанные по ходу работы |
| Что проверяется | форма заполнена | на этапе есть нужные доказательства |

### Описание требования

```
Requirement
  title                  «Фото процесса погрузки»
  kind                   photo | document | signature | scan | number | text | checklist | event | acknowledgement
  min / max              например, фото ≥ 3
  before_phase           до какой фазы должно быть выполнено: started | completed | departed ...
  capture_window         когда собранное засчитывается: например, от «Начато» до перехода
  source                 только камера | камера и галерея
  event_type?            для kind = event: нужно конкретное событие (например, «Пломба установлена»)
  strictness             block — не пускает в фазу | warn — пускает, но отмечает нарушение
  waivable               может ли диспетчер снять требование (с причиной)
  instructions           подсказка водителю: «Снимите каждый ряд паллет»
```

### Откуда берутся требования на этапе

Они **складываются** из трёх источников. При создании рейса
требования копируются на этап, и дальше их можно править для этого рейса.

1. **По типу этапа**, по умолчанию. Например, у всех погрузок перед «Убыл»
   нужны пломба и CMR.
2. **По тегам.** У рейса с `#reefer` перед «Убыл» с погрузки нужна
   температура, а у рейса с `#food` перед «Начато» нужно фото чистого пустого
   кузова.
3. **По конкретному этапу** — из API или от диспетчера. Например, «у этого
   клиента фото каждого паллета».

### Как это выглядит у водителя

1. Требования этапа видны в карточке этапа **сразу по прибытии**: водитель
   заранее знает, что придётся снять.
2. По ходу работы он добавляет фото через кнопку **«Фото процесса»**
   (уточняющее событие). Фото привязываются к требованиям, счётчик
   растёт: `Фото процесса 2 / 3`.
3. При нажатии «Убыл» открывается **чек-лист перехода**:

   ```
   Перед убытием с погрузки:
   ✔ Фото процесса погрузки        4 / 3
   ✖ Фото пломбы                   0 / 1   [Снять сейчас]
   ✔ Номер пломбы                  ABC1234567
   ✖ Подписанная CMR               0 / 1   [Снять сейчас]
   ⚠ Температура (#reefer)          —      [Ввести]
   ```

   То, что можно снять сразу, снимается прямо из чек-листа (если позволяет
   `capture_window`).
4. Требования с `strictness = block` не пускают в фазу. Если выполнить их
   невозможно, водитель нажимает **«Не могу выполнить»** и указывает причину.
   Запрос уходит диспетчеру, и тот снимает требование одним нажатием в чате.
5. **Офлайн.** Требования проверяются на телефоне. Если требование `block`
   нельзя выполнить, а связи с диспетчером нет, водитель может перейти в
   фазу **с нарушением**. Событие помечается `requirements_unmet`, и
   диспетчер увидит это, как только событие дойдёт. Водитель не застревает
   на точке из-за отсутствия связи, но нарушение не теряется.

6. **Убыл без работы** (например, «груз не готов»). Если тип этапа это
   допускает, водитель указывает причину, а требования к работе получают
   отметку «неприменимо»: работы не было, снимать нечего. Это не нарушение,
   но в отчёте такие этапы видны отдельно.

### Как это выглядит у диспетчера

- На этапе видно, какие требования выполнены, чем (с превью фото) и когда.
- Можно добавить требование на этап, снять его или пометить
  «не требуется» с причиной.
- Нарушения (`warn`, снятые требования, переходы офлайн с нарушением)
  попадают в отдельный фильтр и отчёт.

## 4. Где это видно в админке

- **Справочник событий**: карточка с ярлыками и полями, предпросмотр формы
  глазами водителя.
- **Справочник требований и правила по тегам.**
- **Раздел «Автоматы»**: на каждом переходе фазы подписаны требования (см.
  [state-machine.md](state-machine.md#автоматы-в-админке)).
- **Симулятор** показывает, что заблокирует переход для выбранного рейса.
